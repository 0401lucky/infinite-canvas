# Canvas Data Structure

## Storage

This page describes the implemented personal-server storage model. Authentication, persistence, cleanup, and deployment still need the checks in [Pending Tests](/docs/progress/pending-test).

The authenticated, same-origin `server/` application owns business persistence:

| Data | Owner |
| --- | --- |
| Configuration, API keys, canvas projects, assets, prompt sources, installed plugins | SQLite `records`, namespace `app_state` |
| Image/video workbench history, prompt caches | SQLite `image_generation_logs`, `video_generation_logs`, `prompt_cache` namespaces |
| Plugin private JSON | SQLite `plugin:<pluginId>` namespaces |
| Image originals, previews, video, audio, other media | Private files and SQLite `media` metadata |
| Administrator and sessions | SQLite `admin` and `sessions` |

Canvas and asset store keys remain `infinite-canvas:canvas_store` and `infinite-canvas:asset_store`. The full private data directory contains `app.sqlite`, its associated SQLite files, `media/images/`, `media/files/`, `previews/`, and temporary `uploads/`. It must stay outside `web/` and must not be exposed as static content.

Zustand stores hydrate manually after session confirmation. Failed reads are not empty successful data, and failed writes do not fall back to IndexedDB or localStorage. Only tiny machine preferences remain in localStorage. Old browser databases are neither migrated nor deleted automatically. Local Canvas Agent history and message-storage rules remain independent.

## Project

```ts
type CanvasProject = {
  id: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  nodes: CanvasNodeData[];
  connections: CanvasConnection[];
  chatSessions: CanvasAssistantSession[];
  activeChatId: string | null;
  backgroundMode: "lines" | "dots" | "blank";
  showImageInfo: boolean;
  viewport: { x: number; y: number; k: number };
};
```

The viewport stores screen translation in `x` and `y`, and scale in `k`. The canvas store also persists `deletedProjects` for existing WebDAV deletion synchronization; this is separate from image cleanup tombstones.

## Nodes and edges

```ts
type CanvasNodeData = {
  id: string;
  type: CanvasNodeTypeId;
  title: string;
  position: { x: number; y: number };
  width: number;
  height: number;
  metadata?: CanvasNodeMetadata;
};

type CanvasConnection = {
  id: string;
  fromNodeId: string;
  toNodeId: string;
};
```

Node positions and sizes use canvas-world coordinates. Edges store only node IDs; their paths are calculated while rendering. Deleting a node removes its connected edges.

`CanvasNodeTypeId` permits the six built-in kinds (image, text, config, video, audio, group) and extension IDs such as `pluginId:name`. The authoritative types are in `web/src/types/canvas.ts`.

Common metadata includes content, prompt, status, model, dimensions, `storageKey`, MIME type, byte size, and video task identity/provider. A multi-image result remains one node with independently tracked `images` slots; `primaryImageId` selects the node-level result. Image entries and references can also carry `cleared: true`.

`content` and `dataUrl` are runtime display fields, not persistent file identity. SQLite removes temporary `blob:` URLs when a storage key is present. A saved record can therefore have an empty URL and a valid key; hydration must still resolve that key through the authenticated media API. Missing or cleared keys never fall back to an old URL. Text content and non-image metadata remain intact.

## Assistant sessions

```ts
type CanvasAssistantSession = {
  id: string;
  title: string;
  messages: CanvasAssistantMessage[];
  createdAt: string;
  updatedAt: string;
};
```

The in-canvas assistant's message references follow the same media-key rules. Original files are converted to data URLs temporarily only when a browser-direct AI endpoint requires base64. This does not move the separate local Agent's thread/turn/item history into the application database.

## Media lifecycle

`uploadImage()` accepts a Blob, data URL, or remote URL. It downloads the original, verifies that it decodes as an image, uploads it under a new `image:<id>` key, and returns an in-memory object URL and original dimensions. A remote URL that can display but cannot be downloaded is not a saved original: download or storage failure rejects instead of inventing a key. The existing optional local proxy applies to external downloads, never to the application's `/api`.

Video/audio use `uploadMediaFile()` and the same authenticated media service. Restoring a project resolves keys to `/api/media/.../original`; downloads, edits, generation references, ZIPs, and WebDAV read originals through `getImageBlob()` or `getMediaBlob()`. Shared download feedback lives in `use-download-media.ts`.

The existing browser preview queue keeps the 768px-long-edge / WebP 0.86 strategy. It saves previews to the server separately; previews are not authoritative originals and are not included in ZIP or WebDAV backups. Logout, session expiry, and data reload cancel old-session requests and release object URLs and private caches.

## Cleanup and backups

Ordinary node/project/asset/history deletion remains reference-aware. The application collects used keys, and the server refuses individual media deletion while another stored record still references that key.

The settings action **Clear all images** is deliberately different: after confirmation and pending-write flush, it removes all saved image originals and previews, including referenced images. SQLite retains lightweight tombstones and project structure, clears image URLs, and marks old entries as cleared. Account, configuration, text, video, audio, and local Agent history remain. Partial filesystem failure is reported and remaining files still count toward usage; the user can run cleanup again.

Tombstones block stale saves and WebDAV from restoring old keys. ZIP exports retain cleared entries without files; missing originals that are not cleared fail the export. Explicitly importing a ZIP that contains originals creates new keys and remaps nested media references and covers. Importing a cleared package without originals preserves its cleared state. Cleanup does not delete remote WebDAV backups or files already downloaded by the user.

Record writes use revision checks, and WebDAV replaces history collections atomically using the revision captured with the original snapshot. Conflicts require reloading rather than silently merging whole projects. Other already-open browsers need a refresh to see cleanup; this is not real-time collaboration or hosted cloud sync.
