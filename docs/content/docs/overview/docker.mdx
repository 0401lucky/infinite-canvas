# Docker Deployment

The main image now runs a Node.js 24 application service that serves both authenticated APIs and the Vite frontend. This Unreleased deployment flow still needs manual verification; build locally when evaluating it rather than assuming `latest` already contains the changes.

## Configure first

Copy `.env.example` to `.env` and set a strong `ADMIN_PASSWORD`. For a remote deployment, set `APP_ORIGIN` to the exact HTTPS origin used by the browser. Credentials must not go into public `config.js` or a static-assets directory.

## Use the published image

```bash
git clone git@github.com:basketikun/infinite-canvas.git
cd infinite-canvas
cp .env.example .env
# Set ADMIN_PASSWORD and APP_ORIGIN before starting.
docker compose up -d
```

Open `http://localhost:3000`.

## Build locally

```bash
docker compose -f docker-compose.local.yml up -d --build
```

## Documentation image

The documentation in `docs/` is a separate Next.js standalone application with server capabilities.

```bash
cd docs
docker compose up -d
```

To build it from the current source:

```bash
cd docs
docker compose -f docker-compose.local.yml up -d --build
```

## Persistent data and updates

Compose mounts the project-scoped `app-data` volume at `/app/data`. It contains `app.sqlite`, its WAL/SHM files, image originals, previews, other media, and temporary uploads. Do not remove the volume when recreating containers; do not use `docker compose down -v` or prune it as an update step. Stop the application before making a filesystem backup of the complete volume.

Both Compose files use the same volume within the same Compose project. Changing the project name selects a different volume. If you switch to a host-directory mount, its files must be writable by the runtime's `node` user (UID 1000); never place that directory under public static assets.

The application requires Node.js, SQLite, and private media storage, not a static-only deployment. AI provider, prompt-source, and WebDAV requests remain browser-owned. Local Canvas Agent storage remains separate and is not touched by image cleanup. Old browser data is not automatically migrated.

| Setting | Default / behavior |
| --- | --- |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | Username defaults to `admin`; password is required on first start. Explicit username/password changes revoke existing sessions. |
| `APP_ORIGIN` | `http://localhost:3000`; must match the public origin. HTTPS enables Secure session cookies. |
| `SESSION_TTL_DAYS` | 7 days from login, without sliding renewal. |
| `MAX_UPLOAD_MIB` | 512 MiB per file; oversized uploads return 413 without incomplete files. |
| `MAX_JSON_MIB` | 32 MiB per JSON write; oversized requests do not truncate or overwrite stored records. |

There is no login IP rate limiting, account locking, or registration. Use a strong password and HTTPS. Signed-in browsers still receive AI API keys; protect the database, environment file, and backups as secrets. Docker restart/update durability, permissions, SPA routes, plugins, and media Range responses remain acceptance items rather than verified production guarantees.

## Optional analytics

No analytics are enabled by default. A deployment can enable GA4, Baidu Analytics, or both at runtime:

| Variable | Description |
| --- | --- |
| `ANALYTICS_GA4_ID` | Google Analytics 4 measurement ID (`G-XXXX`) |
| `ANALYTICS_BAIDU_ID` | Baidu site ID, the hash after `hm.js?` |

```dotenv
ANALYTICS_GA4_ID=G-XXXXXXXXXX
ANALYTICS_BAIDU_ID=your-site-id
```

SPA route changes automatically report page views to enabled providers. Only configure analytics IDs on sites you control, and do not commit them to the repository.
